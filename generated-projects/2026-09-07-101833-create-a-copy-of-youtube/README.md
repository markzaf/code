## UI/UX Design System
Below is a concise, practical DESIGN SYSTEM for the YouTube‑like platform (mobile‑first, accessible, user‑centered), informed by current video platform trends: minimal chrome, immersive player, dark/light modes, micro‑interactions, clear creator tools, and AI‑assisted UIs.

DESIGN PRINCIPLES
- Mobile‑first responsive: design small screens first; scale up with progressive enhancement.  
- User‑centered: fast discovery, low-friction uploads, clear affordances for creators and viewers.  
- Accessible: WCAG AA+ contrast, large hit targets, keyboard & screen‑reader support.  
- Minimal chrome & immersive content: prioritize the player and video thumbnails; controls fade when idle.  
- Consistent spacing & typography: modular scale for rhythm across screens.  
- Subtle motion: micro‑interactions for likes, uploads, state changes — non‑distracting, reduced‑motion option.

1) BRAND PERSONALITY & TONE
- Personality: confident, helpful, creator‑first, approachable.  
- Tone: direct, encouraging, informative. Copy style: short sentences, action‑oriented CTAs, plain language for tech items (e.g., “Upload video”, “Publish”, “Manage comments”).  
- Microcopy: positive prompts (“Congrats — video published!”), clear error language with actionable remedies.

2) COLOR PALETTE (light + dark support)
Primary system (brand)
- Brand Red: #FF2D55 — energetic CTA, subscribe, record (WCAG AA with neutral text on white? Use carefully).  
- Brand Accent: #0A84FF — secondary CTA, links, highlights.

Neutrals
- White: #FFFFFF  
- Light Gray (surface): #F6F7F9  
- Mid Gray (muted text): #6B7280  
- Dark Gray (text): #111827 — body text on light BG (WCAG AA+).

Dark mode neutrals

- Dark Elevated: #121316

Support colors (status)
- Success: #16A34A (WCAG AA against white)  
- Warning: #F59E0B

Contrast notes
- Body text on light surface: #111827 on #FFFFFF — meets WCAG AA/AAA for normal/large text.  
- Muted text: #6B7280 on #FFFFFF — meets WCAG AA for >=14pt bold or 18pt regular; use for secondary text only.  
- Brand Red (#FF2D55) on white: 3.9:1 — meets WCAG AA for large text/semibold; for small CTAs, use white text on Brand Red (contrast 8.7:1).  
- Dark mode: #E6EDF3 on #0B0D10 — meets WCAG AA.

## Integration, QA & Deployment Guide
Below are concise, actionable Integration, QA, and Deployment instructions for wiring the provided Next.js frontend to the Node/Express/Postgres backend and taking the system to production readiness. Testing and deployment actions must be executed by a developer or CI system — this guidance does not perform those steps.

1) INTEGRATION — wiring frontend ↔ backend (endpoints, env vars, auth & data flow)
- Base URLs & env variables
  - Frontend (Next.js) needs a runtime env var to call the API:
    - NEXT_PUBLIC_API_URL=https://api.example.com (use this in frontend fetches)
  - Backend uses:
    - DATABASE_URL (postgres connection string)
    - JWT_SECRET (secure signing secret)
    - VIDEO_STORAGE_PATH (local only; use S3 key prefix in prod)
    - PORT (server port)
  - Example .env (backend):
    - DATABASE_URL=postgres://user:pass@db:5432/mini_youtube
    - JWT_SECRET=long-random-string
    - VIDEO_STORAGE_PATH=/var/storage/videos
    - PORT=4000

- CORS & security
  - Backend already uses cors(). In production, lock to allowed origins:
    - app.use(cors({ origin: [ 'https://app.example.com' ] }));
  - Enforce HTTPS at load balancer / CDN level.
  - Limit request body sizes and implement rate limiting (e.g., express-rate-limit).

- Authentication flow
  - Signup/login endpoints:
    - POST /api/auth/signup { email, password, displayName } → { token, user }
    - POST /api/auth/login { email, password } → { token, user }
  - Client stores JWT (recommended: in-memory + refresh via httpOnly cookie if you need persistence; current frontend stores none — choose secure storage).
  - Auth header for protected requests:
    - Authorization: Bearer <JWT>
  - Backend middleware requireAuth validates JWT and attaches req.user.

- Key API endpoints (frontend integration notes)
  - GET /api/videos?limit=12&offset=0
    - Returns feed items normalized to { id, title, thumbnail, duration, views, status }.
    - Use on Home page.
  - GET /api/videos/:id
    - Returns video details + increments views. Use for watch page to fetch metadata and storage_path.
    - storage_path currently points to local file path; in prod replace with signed CDN/S3 URL.
  - POST /api/uploads (multipart/form-data)
    - Fields: video file under key "video", optional title, description.
    - Requires Authorization header (Bearer).
    - Response: { id, status } — frontend should poll /api/uploads/:id/status to surface processing state.
  - GET /api/uploads/:id/status
    - Returns processing_status and storage_path.
  - GET /api/comments?video_id=<id>
    - Returns comments.
  - POST /api/comments { video_id, body } (Bearer required)
  - POST /api/videos/:id/like (Bearer required)
  - GET /api/search?q=term

- Video storage & streaming (recommended production changes)
  - Dev: backend exposes /storage/videos static route. For production:
    - Store uploaded files in S3 (or equivalent) instead of local disk.
    - On upload route, upload incoming file to S3, respond with video object referencing S3 key.
    - Use a transcoding worker (FFmpeg / serverless) to produce HLS/DASH and thumbnails.
    - Serve streaming via CDN (CloudFront/Cloudflare) using signed URLs or short-lived presigned URLs.
    - Replace storage_path with signed CDN/HLS master playlist URL returned by API.

- Upload UX considerations (frontend)
  - Implement resumable/chunked uploads (tus, S3 multipart) for large files.
  - After POST /api/uploads returns id, poll GET /api/uploads/:id/status and update UI to "Processing" / "Ready".
  - When ready, API should provide poster_url and streaming URL.

- Event & analytics pipeline
  - Backend writes lightweight events into events table (views, likes, comments). For scaling, forward events to a message queue (Kafka/SNS/SQS) and process asynchronously into analytics store.
